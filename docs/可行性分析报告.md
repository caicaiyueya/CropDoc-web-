# 《云农智诊——基于 NFNet-F1 与大语言模型的农业智能问诊系统》可行性分析报告

## 1 引言

### 1.1 项目背景

农业是国民经济的基础产业，病虫害防治直接关系到粮食安全与农户收益。长期以来，基层农技服务体系面临“人少、面广、响应慢”的结构性矛盾：一方面，专业农技员数量有限，难以对分散农户实现及时上门诊断；另一方面，农户在田间发现叶片斑点、枯黄、霉层等异常时，往往只能依赖经验判断或电话咨询，误判与延误防治时机的情况时有发生。传统人工巡田、纸质记录与单向科普宣传，已难以满足突发性、季节性疫情对快速识别病害、科学指导用药以及经验及时共享的迫切需求。

与此同时，计算机视觉与自然语言处理技术在农业场景中的应用日趋成熟。以深度学习为代表的图像分类模型，已能够在公开植物病害数据集上达到较高识别准确率；大语言模型则具备将结构化识别结果（病害类别、置信度、作物上下文）转译为通俗易懂的防治建议、用药注意事项与农事管理提示的能力。二者结合，可形成从图像感知、智能问诊、社区协作到后台治理的完整数字化服务闭环。

在国家大力推进数字乡村与智慧农业建设的政策背景下，面向农户与农技员构建低门槛、基于浏览器访问的农业智能问诊平台，既是课程设计对软件工程全生命周期训练的需要，也具有明确的现实应用价值。基于上述背景，本课题提出建设《云农智诊》系统，以验证轻量视觉模型、云端智谱 GLM 大模型 API 与 Serverless 业务后端相结合的技术路线在农业问诊场景中的可行性。

### 1.2 项目目标

《云农智诊》的总体目标是：面向普通农户、认证农技员与系统管理员三类角色，构建一套职责清晰、可演示可验收的农业智能问诊系统。系统在技术实现上采用前后端分离与云原生部署思路：表现层采用 Vue3 实现 Web 页面；后端依托微信云开发完成账号、业务逻辑与数据持久化；AI 推理服务部署于微信云托管，基于 FastAPI 承载 NFNet-F1 植物病害分类模型；智能问诊环节通过调用智谱 GLM 大模型 API 完成文本生成，避免本地部署超大规模模型带来的算力负担。

在功能层面，本项目拟达成以下具体目标：

1. **自动化病虫害识别**：支持农户在 Web 端上传或选择农作物叶片图像，经图床获取公网 URL 后，由云托管中的 NFNet-F1 完成推理，返回病害类别与置信度，并持久化为诊断记录。  
2. **智能化问诊建议**：在识别结果基础上，组装结构化上下文调用智谱 GLM 大模型 API，以自然语言输出防治措施、注意事项与后续观察建议，支持多轮追问。  
3. **农技社区协作**：为农户提供发帖求助通道，为农技员提供科普发布与答疑能力，并通过审核机制保障社区内容质量。  
4. **角色化运营管理**：为管理员提供用户与角色管理、帖子审核、病害库与内容维护及基础数据概览，形成可运营的后台治理能力。

### 1.3 可行性分析的目的与范围

本报告依据软件工程中可行性研究的一般方法，从技术可行性、经济可行性、操作可行性、社会可行性四个维度，论证《云农智诊》在课程设计周期内是否具备立项实施条件。分析范围覆盖系统架构选型、关键技术风险（如模型内存溢出、接口超时、跨域上传）、成本构成、多角色易用性以及社会效益与伦理边界，不涉及商业化推广的详细市场调研。

## 2 技术可行性

技术可行性重点回答：在既定约束（课设周期、有限算力、云服务免费额度）下，所选技术路线能否稳定支撑病虫害识别、智能问诊、社区交流与后台管理等主流程，以及关键风险是否存在成熟、可落地的应对方案。

### 2.1 前后端分离架构与工程成熟度

系统采用经典的浏览器与服务器结构，并实行前后端分离。表现层由 Vue3 构建的 Web 页面构成，通过 HTTPS 调用云函数与云托管 REST API 完成交互；业务逻辑、权限校验与数据访问下沉至微信云开发与云托管服务端，浏览器端仅持有登录态与展示逻辑。该模式具有以下优势：

- **职责清晰**：界面演进与业务规则变更可相对独立进行，符合高内聚、低耦合的模块化设计原则。  
- **生态成熟**：Vue3 组合式 API、组件库（如 Element Plus）、路由守卫与状态管理（Pinia）已形成稳定工程范式，页面开发与联调效率高，满足本课程仅交付 Web 端的建设范围。  
- **安全可控**：可采用 JWT 或云开发登录态进行身份鉴别，结合基于角色的访问控制，在网关或云函数层统一拦截越权请求，满足农户、农技员、管理员的分权需求。  
- **可测试、可演示**：前后端通过明确的接口契约协作，便于编写接口测试与集成测试，满足课程设计“可运行、可验收”的硬性要求。

综合来看，前后端分离并非实验性方案，而是业界主流实践，文档与社区案例充足，架构层面的技术风险较低。

### 2.2 NFNet-F1 轻量部署与 OOM 风险对策

病虫害识别是本系统的核心能力之一。NFNet-F1 作为高精度图像分类骨干网络，在公开植物病害任务上表现优异，但权重体积与推理时内存占用相对较大。将其部署于微信云托管等资源受限的容器环境时，若每次请求重复加载模型、输入分辨率过大或并发推理过高，极易触发内存溢出，导致服务崩溃或冷启动失败。因此，技术可行性不仅取决于模型能否识别，更取决于模型能否在云托管约束下稳定推理。

针对上述风险，可采用业界已验证的工程化对策：

| 策略 | 具体措施 | 预期效果 |
|------|----------|----------|
| 推理模式约束 | 使用评估模式、关闭梯度计算；优先采用 CPU 推理，条件允许时可降低数值精度 | 降低峰值内存占用 |
| 输入标准化 | 统一将图像缩放至固定分辨率（如 512×512）并做归一化 | 控制张量规模，稳定单次推理开销 |
| 模型单例加载 | 进程启动时全局加载一次权重，请求路径仅做前向推理 | 避免重复加载导致的内存尖峰与耗时 |
| 并发与限流 | 限制同时推理数量，必要时对请求排队 | 防止瞬时流量叠加引发内存溢出 |
| 服务无状态化 | 推理服务与业务库解耦，容器可水平扩展、故障快速重建 | 提升可用性，隔离识别故障对业务库的影响 |
| 链路解耦 | 前端先上传图床获得 URL，再将 URL 交给推理服务 | 减小请求体、规避跨域与超时，利于排障 |

上述方案可在 FastAPI 与 PyTorch、timm 技术栈中落地实施，使识别服务成为可独立运维的服务节点。结合图床中转与置信度阈值（如低于百分之八十提示重新拍照），可在资源有限条件下兼顾可用性与识别质量。因此，NFNet-F1 的云端部署在采取必要工程约束后，具备技术可行性。

### 2.3 智谱 GLM 大模型 API 接入成熟度

智能问诊若依赖本地部署超大规模参数模型，将面临显卡成本高、运维复杂、课设周期内难以完成的问题。本系统选择调用智谱 GLM 大模型 API：服务端仅需将病害名称、置信度、作物类型及用户问题组装为提示词，通过 HTTPS 发起请求并解析返回文本，即可完成防治建议生成。

该方案的成熟度体现在：

1. **接口标准化**：智谱 GLM 大模型 API 文档完善，提供稳定的 HTTP 调用方式与示例，集成周期短。  
2. **算力外包**：训练与推理算力由云端服务承担，项目组无需购置 GPU 服务器，显著降低技术门槛与运维复杂度。  
3. **工程可控性**：可对调用设置超时（如六十秒）、失败重试、降级文案以及上下文长度裁剪，属于常规接口工程能力。  
4. **与识别结果解耦**：视觉模型负责判定病害类别，智谱 GLM 大模型 API 负责生成防治建议，二者通过结构化字段衔接，便于分别优化。

因此，智谱 GLM 大模型 API 接入路径清晰、依赖外部成熟服务，技术风险总体可控。

### 2.4 关键技术路径小结

系统主链路可概括为：用户在 Web 端选择图片后上传至图床并获得 URL，再由云托管中的 NFNet-F1 完成推理，业务库写入诊断记录并由前端展示结果；在需要时进一步调用智谱 GLM 大模型 API 生成问诊建议。该路径各节点均有成熟组件支撑，失败点可定位、可降级，满足软件工程对可维护性与可观测性的基本要求。

**技术可行性结论**：所选技术栈成熟度高，文档与社区支持充分；内存溢出、跨域、超时等已知风险均有对应对策；关键业务路径清晰可实现。故本项目在技术层面具备实施可行性。

## 3 经济可行性

经济可行性从开发成本与运维成本两方面评估：在课程设计场景下，系统是否能够以接近零的额外资金投入完成建设、联调与演示。

### 3.1 开发成本分析

本项目属于高校软件工程课程设计，研发人力由学生团队在教学周期内投入，不产生额外薪酬成本。技术选型上优先采用开源框架与云平台免费能力：

| 成本类型 | 内容 | 课设阶段评估 |
|----------|------|----------------|
| 人力成本 | 需求分析、设计、编码、测试、文档撰写 | 由课程学时覆盖，不计现金支出 |
| 开发工具 | 代码编辑器、浏览器调试工具、Git 等 | 免费或已有授权 |
| 前端框架 | Vue3、Vite、组件库等 | 开源，授权费用为 0 |
| 后端与 AI | 云开发、FastAPI、PyTorch、timm、模型权重（按许可使用） | 开源或可合法获取，无商业授权费 |
| 学习与资料 | 官方文档、开源社区、课程讲义 | 基本免费 |

综合可见，除团队已有电脑与网络环境外，因本项目直接产生的商业软件采购成本可视为零元，开发成本在经济上完全可承受。

### 3.2 运维成本分析

系统上线演示后的主要开销来自云资源与第三方 API 调用。针对课设流量规模（用户量小、并发低、演示时段集中），各项成本均可控制在免费额度或极低水平：

| 成本项 | 计费特点 | 课设阶段评估 | 说明 |
|--------|----------|--------------|------|
| 微信云托管 | 按资源与调用量计费 | 低 | 演示级访问量下通常处于免费或低费用区间，需关注冷启动而非费用 |
| 图床服务 | 免费接口密钥 | 0 | 用于图片公网分发，避免自建对象存储初期成本 |
| 智谱 GLM 大模型 API | 按调用量计费，常有新用户或学生免费额度 | 低，阶段性可为 0 | 联调与答辩演示的 Token 消耗有限 |
| 域名与证书 | 可用默认域名或本地演示 | 0 | 课设阶段可不购买独立域名 |

在课设演示规模下，系统可实现低成本乃至近似零边际成本运行。若未来扩展为区域性农技服务平台，再按日活用户、图片存储量与 Token 消耗进行弹性扩容与预算评估即可，不构成当前立项与实施的经济障碍。

### 3.3 成本与收益定性评估

从投入产出角度看：有限的时间与近零资金投入，可换取一套覆盖病虫害识别、智能问诊、社区交流与后台管理的可运行 Web 系统，以及覆盖需求分析、UML 建模、实现与测试的全套工程文档，对课程目标的达成具有较高性价比。

**经济可行性结论**：开发成本近似为零，运维成本在免费额度内可控，经济上完全可行。

## 4 操作可行性

操作可行性关注系统交付后，目标用户能否以可接受的学习成本完成其核心任务，以及界面与流程是否符合各角色的使用习惯。

### 4.1 面向普通农户的易用性

农户是本系统的主要服务对象，其信息化水平参差不齐，操作设计必须遵循路径短、反馈强、容错好的原则。Web 页面围绕选图上传、一键识别、查看结果、发起智能问诊设计最短任务路径：用户无需理解模型原理或填写复杂表单，即可完成初诊。针对识别失败、网络异常或置信度偏低等情况，系统通过明确文案引导用户重新拍照、保证叶片清晰、避免上传非作物图片，从而降低误操作与挫败感。浏览器端即可完成全部操作，符合本课程仅建设 Web 页面的范围，操作可行性高。

### 4.2 面向农技员的易用性

农技员在完成认证后，主要使用社区侧的发布科普、解答疑问、专业评论等能力。该类交互与常见内容社区高度同构，学习迁移成本低。农技员亦可查看农户识别结果上下文，提高答疑针对性。系统通过角色权限区分农户求助帖与农技科普帖，避免功能菜单冗余，保证专业用户高效完成知识供给任务。

### 4.3 面向管理员的易用性

管理员通过独立后台完成用户管理、帖子审核、病害库维护与数据概览。界面采用常见的侧边导航与列表表单模式，符合管理信息系统的操作习惯；路由守卫与接口鉴权双重约束，减少误入无权限页面的情况。审核流程中待审、通过、驳回、下架等状态清晰，便于批量处理与责任追溯，满足运营侧日常操作需求。

### 4.4 培训与推广成本

因交互范式贴近主流网站后台与表单操作，课设演示与答辩场景下仅需简短操作说明即可上手；若面向真实农户试点，可通过一页图文说明书与村级农技员带教完成推广，无需长时间专项培训。

**操作可行性结论**：多角色任务边界清晰，主路径短、异常可恢复、管理习惯符合常规后台，操作可行性良好。

## 5 社会可行性

### 5.1 对智慧农业与数字乡村的积极意义

《云农智诊》将计算机视觉与智谱 GLM 大模型能力下沉到田间问诊场景，有助于提升病虫害初筛效率，缩短发现问题到获得建议的时间窗口，契合智慧农业用数据辅助农事决策的发展方向。对数字乡村建设而言，系统可作为基层农技服务的数字化补充渠道，尤其在偏远或农技员稀缺地区，具有缓解服务不均衡的潜力。

### 5.2 对基层农技服务体系的补充作用

本系统并不试图替代县乡农技站的专业职能，而是定位为辅助决策与知识扩散工具：农户获得即时、可理解的初诊与防治提示；农技员通过社区沉淀经验、扩大服务半径；管理员保障账号安全与内容合规。三者协同，可形成机器初诊、人工复核与社区互助相结合的分层服务模式，有利于提升基层农技服务的响应速度与覆盖面。

### 5.3 社会接受度与伦理合规

图像识别与智能生成文案均存在误差可能，系统设计强调置信度展示、低置信度时引导重新拍照，以及建议仅供参考、严重病情请咨询当地农技部门等提示，符合技术伦理与负责任创新要求。社区内容经审核后公开，有助于抑制谣言与不当用药信息传播。在合法合规使用用户上传图片与账号数据的前提下，项目社会接受度较高，不存在明显的制度性或舆论性障碍。

**社会可行性结论**：项目对智慧农业与基层农技服务具有正向价值，定位清晰、伦理边界明确，社会可行性良好。

### 6.2 实施建议

为降低交付风险，建议采用增量迭代策略：优先打通从图片上传、图床中转、模型推理、记录落库到结果展示的识别闭环，尽早暴露内存溢出、跨域与冷启动问题；在此基础上推进智能问诊与社区功能，以识别上下文驱动智谱 GLM 大模型 API，以审核机制保障社区质量；同步完善管理后台，保障用户权限、内容合规与演示数据可维护；文档与 UML 模型与实现同步更新，确保课程设计各阶段产出完整、可追溯。

在上述安排下，项目可在教学周期内完成可运行的 Web 系统与配套工程文档，达到验收标准。
